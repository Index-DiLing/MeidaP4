## 1. 本轮修掉的 3 个真机 bug（都是"离线全绿、上电才炸"）

### B1 · `tskNO_AFFINITY` 被 esp_tinyusb 拒绝 → 整个 USB 不起来
```
E tinyusb_task: tinyusb_task_check_config(109): Task affinity should be less or equal to CPU amount
E usb_composite: tinyusb_driver_install 失败: ESP_ERR_INVALID_ARG
```
- 位置：`components/usb_composite/usb_composite.c`（Lead 的代码）
- 根因：`tinyusb_task_check_config()` 判据是 `xCoreID <= SOC_CPU_CORES_NUM`，
  而 `tskNO_AFFINITY = 0x7FFFFFFF` ⇒ 恒失败。
- 修复：`cfg.task.xCoreID = 1;`（P4 双核，合法值 0/1）

### B2 · `usb_net` 桥接符号在 NAPT 模式下无守卫 → 链接失败
```
usb_net.c:934: undefined reference to `usb_net_bridge_set_upstream'
```
- 位置：`components/usb_net/usb_net.c:920`（WS-net 的代码，Lead 介入修）
- 根因：`usb_net_bridge.c` 只在 `CONFIG_APP_USBNET_MODE_BRIDGE=y` 时进 SRCS，
  而调用处只有**运行期** `if`，没有 `#if` 守卫。同文件其余 4 处 bridge 调用都有守卫，只漏这一处。
- 修复：用同一个宏守卫调用。

### B3 · 入口选择不能用 Kconfig、也不能用 `-D`
- 现象：日志出现**两条**入口 STATUS，`main_prod.cpp` 的编译行却带着 `usb_probe`/`mtp_probe` 的 include
  → `fatal error: mtp_backend.h: No such file or directory`
- 根因：IDF 的 component manager 在"缺 Kconfig 值"时**重跑一次 configure**；
  第一遍 `sdkconfig` 还没生成 ⇒ `CONFIG_*` 全空 ⇒ 走错分支且**第一遍已生效**。
  用 `-DMEIDAP4_MODE=prod` 也不行（第一遍不可见）。
- 修复：改用**环境变量** `MEIDAP4_MODE`（被所有子进程继承，第一遍就可见），
  `main/CMakeLists.txt` 只依赖它。
- **教训（已写进代码注释）**：**构建结构只能依赖"第一遍 configure 就可见"的输入。**

## 2. 描述符与规范逐条核对（设备侧 hexdump，非推断）

设备开机打印 HS/FS 配置描述符全文，逐条对照 USB 2.0 / CDC-NCM 1.0 / MS OS 2.0：

- device：`12 01 10 02 EF 02 01 40 3A30 4103 0001 01 02 03 01` ✅（bcdUSB=0x0210 才取 BOS）
- config：`09 02 A3 00 05 01 00 80 FA` → wTotalLength=163、bNumInterfaces=5、bMaxPower=500 mA ✅
- IF0 MTP `06/01/01` 3 EP ✅ · IF1 video `FF/00/00` 1 EP ✅ · IF2 ctrl `FF/00/00` 2 EP ✅
- IAD `08 0B 03 02 02 0D 00 00` → first=3 count=2 class 02/0D/00 ✅
- IF3 NCM 控制 `02/0D/00` + HEADER(5) + UNION(5) + **ECM(13)** + **NCM(6)** + 通知 EP(16 B, interval 8) ✅
  （ECM 的 `iMACAddress=7` 正确指向 MAC 串 —— 这就是 I1 需要 `extra_string` 的原因）
- IF4 数据 `0A/00/01` **alt0(0 EP) + alt1(2 EP)** ✅（Windows 收件箱 NCM 驱动的标准形态）
- BOS 57 B：WebUSB UUID + `iLandingPage=0` + MS OS 2.0 UUID ✅
- MS OS 2.0 166 B：Set Header → Function Subset(IF2=2) → `WINUSB` → **单数 DeviceInterfaceGUID + REG_SZ** + `{A5DCBF10-…}` ✅
  （真机侧 `msos_req=1`，说明 **Windows 确实来取了 MS OS 描述符**；`webusb_get_url=0`，符合 `iLandingPage=0`）

**⇒ 描述符本身没有找到任何违规。问题不在我们拼的字节。**

## 3. 🔴 阻塞项：`netd_open()` 缺接口类守卫（上游缺陷）

### 现象（TinyUSB 自身日志，`CONFIG_TINYUSB_DEBUG_LEVEL=2`）
```
Set Configuration
  Open EP 81 with Size = 64      ┐
  Open EP 02 with Size = 512     ├ 这是 **MTP 的三个端点**
  Open EP 82 with Size = 512     ┘
  NET opened                     ← 被 **NET 驱动**打开了！
  Open EP 83 / VENDOR opened     ← IF1 视频，正确
  Open EP 84, EP 04 / VENDOR opened  ← IF2 控制，正确
netd_open 905: ASSERT FAILED
process_set_config 1296: ASSERT FAILED
  Stall EP0
```
（Windows 重试 3 次，每次同样失败 → `CM_PROB_FAILED_START`）

### 根因
`managed_components/espressif__tinyusb/src/class/net/ncm_device.c:904`：
```c
uint16_t netd_open(uint8_t rhport, tusb_desc_interface_t const *itf_desc, uint16_t max_len) {
  TU_ASSERT(ncm_interface.ep_notif == 0, 0);   // ← 第一行就是这个，**没有 bInterfaceClass 检查**
```
对照同类驱动 `vendor_device.c:285` 有守卫：
```c
TU_VERIFY(TUSB_CLASS_VENDOR_SPECIFIC == desc_itf->bInterfaceClass, 0);
```

机制链：
1. NCM 与 MTP 都是**应用层驱动**（`usbd_app_driver_get_cb`），且被**排在内建驱动之前**
   （`usbd.c:392` 注释原文 "Application is positioned first"）。
2. esp_tinyusb 注册顺序是 **NET 先、MTP 后**（串口 `NET init` 先于 `MTP init`）。
3. `netd_open` **没有类守卫** ⇒ 对**任何**接口都会尝试 ⇒ 直接抢走配置里的**第一个**接口 = MTP 的 IF0。
4. 到真正的 NCM 接口（IF3）时 `ep_notif` 已非 0 ⇒ 断言失败 ⇒ `process_set_config` 失败 ⇒ stall EP0。

### 为什么必然发生，与接口顺序无关
`netd_open` 会抢**它遇到的第一个接口**。所以：
- 任意顺序下，**只有把 NCM 放在第一**才能让它抢对；但那样 MTP 的接口号/端点号全部要重排，
  等于推翻 `frozen-allocation` §1/§2 与 verifier 的 389 条断言。
- 把 MTP 排到 NET 前面也没用：netd 会转而抢下一个未被内建驱动认领的接口（vendor 之后仍是它）。

**⇒ `esp_tinyusb 2.3.0 + TinyUSB 0.21.0~2` 下，MTP 与 NCM 无法共存于一个复合设备**，
这是上游未测试过的组合（esp_tinyusb 自带的默认描述符同样把 MTP 排在 NET 之前）。

### 两个修法
| 方案 | 改动 | 代价 | 评价 |
|---|---|---|---|
| **A. 补一行类守卫**（推荐） | 把 `espressif/tinyusb` vendor 成本地组件（`override_path`），在 `netd_open` 第一行加 `TU_VERIFY(TUSB_CLASS_CDC == itf_class && TUSB_CDC_SUBCLASS_NCM == itf_subclass, 0);` | 仓库里多一份 tinyusb 源码；**冻结表完全不动** | ✅ 保住全部契约与 389 条断言；一次性消除该类问题 |
| B. 把 NCM 排到 IF0/IF1 | 改 `frozen-allocation` §1/§2、所有端点号、verifier 断言、plan §1 | 大 | ❌ 为绕上游 bug 推翻自己的契约 |

**推荐 A。** 且这个补丁与被 patch 的缺陷都可精确引用（`ncm_device.c:904` / `usbd.c:392`）。
