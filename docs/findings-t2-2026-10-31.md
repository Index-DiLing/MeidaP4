## 2. 🔴 真机才暴露的 5 个数据面 bug（都表现为"看起来在跑，主机 0 帧/超时"）

### B1 · `webusb_proto_ep_write()` 只认控制 IN，**把 EP3 的视频帧全丢了**
- 位置：`components/webusb_proto/webusb_proto.c`
- 旧代码：`if (!s_eps_valid || ep_in != s_ep_in ...) return 0;` —— `s_ep_in` 是**控制**端点 0x84，而视频任务写的是 0x83。
- 现象：设备侧 `Video frames=334` 在涨，`Vendor frames_sent=0 / dropped` 在涨，主机一帧收不到。
- 修复：放开"只收 s_ep_in"限制，端点合法性交给 `usb_composite_ep_write()`（未知端点天然返回 0）。

### B2 · `usb_composite_ep_write()` 的合成 `pending` 计数器与 TinyUSB 异步续传打架 → 端点**永久卡死**
- 位置：`components/usb_composite/usb_composite.c`
- 旧实现：`pending = accepted - flushed`。esp_tinyusb 的 vendor 驱动是 **FIFO + 完成回调里自动续传**（`vendord_xfer_cb` 在 TX complete 时自己调 `tu_edpt_stream_write_xfer`），FIFO 会被驱动**异步**排空；于是端点忙时 `pending` 变大、之后 `flush` 因 FIFO 已空而返回 0 ⇒ `pending` 永远减不下去 ⇒ **所有后续写返回 0**。
- 真机现象：EP4 只出 `HELLO`+`PING` 两帧（36 B）后彻底静默，`in_bytes` 不再增长；Windows 侧读 EP4 永远超时。
- 修复：`ep_write_pending()` 直接返回**驱动 TX FIFO 占用**（`CFG_TUD_VENDOR_TX_BUFSIZE - tud_vendor_n_write_available()`）；`ep_write()` 按 FIFO 可用空间收数据、尽量 flush、推不完交给完成回调续传。

### B3 · `link_down` 标志顺序错误 → 刚 `link_up` 就被上一轮陈旧标志掐死
- 位置：`components/webusb_proto/webusb_proto.c`（`wu_drain_rx` 末尾的延迟动作）
- 旧顺序：先处理 `s_flag_link_up` 再处理 `s_flag_link_down`。真机日志同毫秒出现
  `link_up：收到 HELLO_ACK` 紧跟 `link_down: 3 s 未收到有效帧` —— 标志是主机不在时重传耗尽置上的，却在新链路建立后被消费。
- 修复：**先 link_down、后 link_up**（本轮收到的 HELLO_ACK 生效）。

### B4 · 链路超时判断用无符号差值 → `link_up` 后立即下溢判死
- 位置：同上，`wu_poll_timers()` 的 `§6.3 3 s 超时`
- 根因：`t` 是 `wu_task` 循环开头取的；`wu_do_link_up()` 在本次 `wu_drain_rx()` 里用**更晚**的 `wu_now_ms()` 更新 `s_last_rx_ms`。无符号 `(uint32_t)(t - s_last_rx_ms)` 下溢成 ~4.29e9 ⇒ 立刻 `link_down`。
- 真机现象：偶发"握手成功但视频 0 帧"，日志里 link_up/link_down 同毫秒。
- 修复：改成**有符号**比较 `(int32_t)(t - s_last_rx_ms) >= 3000`。

### B5 · 视频任务一次部分写就整帧作废（720p 帧 48–62 KB > 8 KB FIFO）
- 位置：`components/usb_vendor/usb_vendor_video.c`
- 旧实现：`w = ep_write(...); if (w != flen) return false;` —— FIFO 必然写一半就满，于是**每一帧都被判废**。
- 修复：新增 `video_write_msg()`：在 100 ms 预算内循环写直到整条消息进 FIFO；超时才丢帧并 `report_drop`。同时删掉"FIFO 占用 > 阈值就跳帧"的门控（真机上导致 `stale_skip=843`，几乎每帧被跳过）。

### B6 · 🔴 VIDEO 分片违反 §5.2：**每个协议帧都塞了 16 B 视频头** → 网页花屏/错位
- 位置：`components/usb_vendor/usb_vendor_video.c`（`video_send_message()`）
- 协议 `docs/protocol.md §5.2` 明确：**一条消息 = 一整个编码帧**；16 B 视频头只在消息开头出现**一次**；
  消息超过 `WU_MAX_PAYLOAD(1024)` 时按普通协议分片（`MORE=1` = "同一条消息还有分片"）。
- 旧实现：把 1036 B 的每个协议帧都做成 `[16 B 视频头][1008 B 数据]`，并用 `MORE` 表示"同一帧的下一片"。
- **真机现象（浏览器里）**：画面横向错位、色带/偏色、闪烁 —— 因为网页严格按协议用 `Assembler`
  把带 `MORE` 的分片拼成整条消息，于是**除第一片外每个分片前面的 16 B 头都被当成 JPEG 像素数据**拼进图像。
- 为什么之前"没发现"：`tools/webusb_app.py` 当时按旧语义"逐帧解析"，所以它导出的 JPEG 是好的
  （**工具与固件用了同一个错误假设，互相掩盖**）。这次用"把真实 EP3 原始流回放给网页自己的 Video 模块"
  才把两边区分开。
- 修复：按协议重写发送逻辑 —— 视频头只在 frag0 出现，后续 frag 是纯 JPEG 续片；
  `chunk_index` 恒 0；`frame_seq` 只在完整帧上 +1；并加整帧发送预算（1.5 s）避免长期占着缓冲。
  修复后：同一份 EP3 流经网页 `Video` 模块重组出的首帧与设备端画面完全一致（无错位/偏色）。
- ⚠️ 教训：**客户端实现与固件共享同一个错误假设时，两边都会"自证清白"**。跨实现验证必须
  让"真实数据"流过**另一套独立实现**（这里：网页代码 + 回放真实抓包）。

### B7 · 🔴 引导期 `PING(seq=0)` + "无效帧也刷新超时" ⇒ 序号死锁（网页无画面/几百帧后卡死）
- 位置：`components/webusb_proto/webusb_proto.c`（`wu_poll_timers` / `wu_on_frame`）
- 真机指纹（浏览器 LOG 面板）：
  `通道 CTRL 出现 seq 空洞：收到 569，期望 1`、`dup=582 gap=88 retx=64`、
  `链路 down（retx_exhausted）` 每 1–2 s 循环一次；偶尔先出几百帧再卡死。
- 机制（两个缺陷叠加）：
  1. 设备在**引导期**（link_down 等 HELLO_ACK 时）每 1 s 发一条"无状态 PING"，其 seq 恒为 0。
     主机侧可靠通道的 seq 门**只豁免 HELLO_ACK**，于是把它当正常可靠帧接受、把 `rx_expect` 推到 1。
     设备随后 link_up，从 **seq=0** 重新开始 ⇒ 主机 expect(1)、设备 seq(0) 永久错位。
  2. 设备在 `wu_on_frame()` **一进来**就刷新 `s_last_rx_ms`（包括被 seq 门丢弃的帧）⇒
     主机发来的错位帧虽然全被丢，却仍让设备"看起来活着" ⇒ 设备永不判 link_down ⇒
     永不重发 HELLO ⇒ 主机等不到重同步 ⇒ 死锁。
- 修复：
  - 设备**删掉引导期的 PING(seq=0)**（引导期只发 HELLO），保证 link_up 后第一条可靠帧是 seq=0；
  - `s_last_rx_ms` 只在**通过 seq 门/引导帧**后更新（§6.3 的判据是"有效帧"）；
  - 网页侧增加**连接后主动 HELLO_ACK**（`30_link.js: helloHandshake()`，state!=='up' 时每 250 ms 一次，
    最多 15 s）—— 强制设备走一次 §6.3 归零，避免与"上一台主机残留序号"死锁。
- 修复后真机（同一套工具，25 s 连续）：设备侧 **33.66 fps / 16.9 Mbps / dropped=0 / link_up 全程稳定
  （gen=2，无一次 retx）**；主机侧 **844 帧/25 s = 33.8 fps**，JPEG 全合法、gaps=0；
  其间穿插 FILE 通道 LIST/WRITE/READ/DOWNLOAD/MKDIR 全部 PASS。

### B8 · 🔴 ACK 帧占通道 seq ⇒ 丢一条 ACK 就永久死锁（浏览器周期性 `retx_exhausted` 的真因）
- 位置：`components/webusb_proto/webusb_proto.c`（`wu_send_ack` / `wu_on_frame`）+ `web/proto.js`（`ackReceivedFrame` / `_onFrame`）
- 协议原文 §6.5② 要求"每个帧（含 ACK）都吃一个 seq"。但 §6.5③ 又规定 ACK 帧**不进重传窗口、丢了不补发**。
  两者叠加 ⇒ 只要**任意一条 ACK 在 USB 上丢失**，接收方 `expected` 就永久停在旧值：
  之后所有数据帧被判 gap → 发送方重传 5 次 → link_down → 重连后同一条 ACK 再丢 → 无限循环。
- 真机指纹（浏览器 LOG 面板 / 设备状态行）：`gap` 单调增长、`dup=0`、`retx` 增长、
  每 1–2 s 一次 `retx_exhausted`；设备侧 `rxexp` 很小而 `txnext` 已走远、`win` 只有 0–1。
- 修复（**协议修订，已写进 docs/protocol.md §6.5②**）：ACK 帧 `seq=0`、**不推进**通道 seq；
  接收方在 seq 门之前按"长度 4 + 首字节 0x05"识别并消费 ACK，**不**计期望值。
  三端同步：设备 `webusb_proto.c`、页面 `web/proto.js`（app.html 重新生成）、验收工具 `tools/webusb_app.py`。
- 修复后：主机侧 15 s **490 帧（32.7 fps）**、`jpeg_ok=490/490`、FILE 全 PASS；设备侧 `link_up` 全程稳定。

### 另外修掉的 2 处
- `components/file_service/file_service.c`：`op % 2 != 0` 误把 **MKDIR(11)** 当"响应类"吞掉 ⇒ 主机 MKDIR 永远超时。改为 `op != WU_FILE_MKDIR && (op % 2) != 0`。
- `components/ui/ui.c`（WS-V）：ESP-IDF 的 FATFS VFS **没有实现 `statvfs`**，UI 因此永远显示 `SD not mounted`。改用 `sd_storage_is_mounted()` + `sd_storage_get_capacity()`（内部 `esp_vfs_fat_info`）。

## 5. 待办 / 已知限制（诚实口径）

1. **浏览器真机 claim 还没做**：`web/app.html` 需要你在 Chrome/Edge 里点一次「连接设备 → MeidaP4 Composite」。
   离线已用真实 Chrome 跑通"分片→重组→JPEG→canvas"；设备侧数据面已由 WinUSB 工具独立验证。**离线 PASS ≠ 浏览器真机通过**，这一步只能由人点一次（WebUSB 需要用户手势）。
2. **主机工具测到的 fps 波动大（4–28 fps）**：`tools/webusb_app.py` 是 Python + ctypes 的简化主机侧，ACK/读循环不如浏览器/Chrome 的 C++ 实现；**设备侧同一窗口实测 31.4 fps / 1.87 MB/s**（串口 `Video: fps_x100=3137 kbps=14947`）。判据以设备侧与浏览器实测为准。
3. **FILE 通道吞吐**：单条 1012 B、串行等响应 ⇒ 190 KB 页面写入约 200 个事务；大文件（≥100 MB）不实用（协议本身如此）。建议网页文件管理只做"小文件/页面分发"，大批量走 MTP。
4. `fseek` 32 位：≥2 GiB 偏移返回 `EINVAL`（协议 offset 是 u32）。
5. FATFS 并发写同一文件 = 后写者胜，无仲裁（MTP+FILE 同时写同一文件属真机项）。
6. `web/selfcheck.mjs` 预存在失败（引用不存在的 `web/index.html`），与本轮无关，未改动。
7. WiFi 共享 / H.264 / NCM 上网本轮未做。
